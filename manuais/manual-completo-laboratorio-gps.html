1. Para que serve esta tela?

O Laboratório GPS é uma interface web de diagnóstico. Ele consulta uma API local, recebe uma lista de dispositivos, apresenta dados em uma tabela e desenha pontos num gráfico geográfico simplificado. Seu objetivo é permitir que você enxergue o caminho dos dados antes de integrar os veículos ao mapa 3D principal.

Os quatro carros vistos no teste são simulados. Eles não representam trânsito real, pessoas ou veículos monitorados fisicamente. A interface principal do Geo Intelligence e a tela de laboratório são módulos diferentes; cada projeto WMK pode operar independentemente.

Resultado já observado: usando http://127.0.0.1:8766, a tabela mostrou quatro veículos, coordenadas, velocidades e horários. O usuário confirmou que as velocidades mudam com a atualização automática de dez segundos. Isso valida o fluxo do simulador para esta página, mas não valida ainda o Tracker autenticado nem o mapa 3D principal.

3. Guia do usuário — reproduzir o teste aprovado

  1. Deixe o simulador Python de carros funcionando, como no teste anterior.
  2. Mantenha ativa a ponte GPS local da porta 8766.
  3. Abra /geo-bridge-lab.html no Vite, normalmente http://127.0.0.1:4173/geo-bridge-lab.html.
  4. Em Endereço do Bridge, digite http://127.0.0.1:8766.
  5. Clique em Atualizar veículos e observe quatro linhas.
  6. Marque Atualizar a cada 10 s e observe se as velocidades e horários das posições mudam.
  7. Se quiser interromper as consultas automáticas, desmarque a opção. Isso não desliga o simulador Python.
Como ler o resultado: o número 4 indica que a ponte devolveu quatro registros. A variação de velocidade confirma que a página recebeu dados atualizados. Para provar persistência no Traccar, é necessário outro teste com a API autenticada.

4. Arquitetura e responsabilidade de cada programa

[Python simular-carros.py] │ gera posições fictícias ▼ [posicoes-simuladas.jsonl] │ arquivo de eventos ▼ [wmk_bridge.py :8766] │ GET /api/v1/vehicles │ JSON HTTP + CORS ▼ [geo-bridge-lab.js :4173] │ fetch() + validação ▼ [bridgeAdapter.js] │ array de veículos normalizados ▼ [Tabela HTML + pontos SVG] Caminho alternativo (ainda não autenticado neste teste): [Tracker :8082] → [WMK Geo Bridge :8768] → [Laboratório]

A porta 8766 pertence à ponte de laboratório que lê os arquivos simulados. A porta 8768 pertence ao serviço independente WMK Geo Bridge e, na configuração observada, retornou HTTP 503 por falta de credenciais do Tracker. Não são o mesmo processo.

Trecho 1 — consulta HTTP com fetch

const response = await fetch(base + '/api/v1/capabilities');
if (!response.ok) throw new Error('HTTP ' + response.status);
const capabilities = await response.json();

fetch() faz uma requisição HTTP; await aguarda a resposta sem bloquear a interface; response.ok indica status 2xx; .json() interpreta o corpo JSON.

Trecho 2 — a consulta de veículos

const items = await fetchBridgeVehicles({ base });
// items é um array de veículos normalizados

A função está no adaptador. Ela chama GET /api/v1/vehicles, verifica o status, exige schemaVersion: "1.0" e items como array e transforma cada veículo por normalizeBridgeVehicle(). Isso evita que a interface precise entender todos os detalhes da resposta bruta.

Trecho 3 — atualização automática

setInterval(() => {
  if (document.getElementById('auto').checked) refresh();
}, 10000);

10000 representa 10.000 milissegundos = 10 segundos. A função refresh() verifica um sinalizador busy para não iniciar outra consulta enquanto a anterior ainda está em andamento. Esse mecanismo é chamado polling; não é WebSocket nem push em tempo real.

Trecho 4 — segurança ao montar a tabela

const td = document.createElement('td');
td.textContent = String(value);
tr.append(td);

Usar textContent para dados externos evita que textos vindos da API sejam interpretados como HTML. O desenho de pontos usa createElementNS porque SVG tem um namespace próprio.

6. Fluxo completo de uma atualização

  1. O simulador registra novas posições no arquivo JSONL.
  2. A ponte Python recebe a requisição HTTP /api/v1/vehicles.
  3. Na fonte simulada, a ponte lê o cadastro de veículos e procura a última posição registrada de cada ID.
  4. A ponte responde JSON com schemaVersion, source, items e count.
  5. O navegador recebe os bytes da resposta por HTTP.
  6. O adaptador verifica o contrato e normaliza nomes, coordenadas, velocidade e horário.
  7. O JavaScript apaga as linhas anteriores e cria novas células para cada veículo.
  8. Para posições válidas, desenha um círculo SVG proporcional às coordenadas.
  9. A mensagem de status exibe a hora local em que a consulta terminou.

Coordenadas no SVG: o código transforma longitude de −180 a +180 em eixo X de 0 a 1000 e latitude de +90 a −90 em eixo Y de 0 a 300. É uma projeção esquemática, não uma projeção cartográfica adequada para medir distâncias.

const x = (longitude + 180) / 360 * 1000;
const y = (90 - latitude) / 180 * 300;

7. Entendendo o JSON da API

Exemplo fictício e simplificado do contrato da ponte:

{
  "schemaVersion": "1.0",
  "source": "simulator",
  "count": 1,
  "items": [{
    "id": "WMK-NF-CARRO-001",
    "name": "Carro de teste 01 - Centro",
    "simulated": true,
    "position": {
      "latitude": -22.2827,
      "longitude": -42.5320,
      "speedKmh": 37,
      "heading": 90,
      "timestamp": "2026-11-07T00:55:13+00:00"
    }
  }]
}

schemaVersion permite evoluir o contrato; source identifica a origem; count informa a quantidade; simulated: true declara dados fictícios; position pode ser null se o dispositivo não tiver posição. No navegador, a tabela usa latitude, longitude, speedKmh e timestamp.

Para inspecionar o JSON diretamente, abra a API de veículos simulados ou use PowerShell:

Invoke-RestMethod 'http://127.0.0.1:8766/api/v1/vehicles?source=simulator' |
  Select-Object source, count, items

Limitações atuais identificadas no código: a tela não diferencia perfeitamente as duas versões de /capabilities; não indica visualmente a fonte simulada; e pode manter linhas antigas após uma consulta falhar. Essas melhorias são recomendadas antes de uso operacional.

9. Segurança, privacidade e boas práticas

Dados de localização podem ser sensíveis. Nunca publique coordenadas de pessoas sem autorização. O Bridge de laboratório foi configurado para loopback 127.0.0.1, e não deve ser exposto à internet sem autenticação, autorização, HTTPS, controle de acesso e auditoria. O navegador não deve receber senha do Traccar: a autenticação, quando necessária, fica no servidor Bridge.

O endpoint de laboratório mostra dados fictícios. Para produção, também será necessário validar entradas, controlar o intervalo de consultas, distinguir posições antigas de recentes, tratar indisponibilidade e limitar quais dispositivos cada usuário pode visualizar.

10. Exercícios de aprendizagem

  1. Iniciante: clique em Atualizar veículos e identifique a diferença entre horário da consulta e horário UTC da posição.
  2. Iniciante: desmarque atualização automática e explique por que a tabela deixa de mudar.
  3. Intermediário: abra /api/v1/vehicles?source=simulator e localize o objeto position do primeiro veículo.
  4. Intermediário: identifique em geo-bridge-lab.js onde o botão Atualizar veículos é conectado ao evento de clique.
  5. Desenvolvedor: explique por que textContent é preferível a inserir HTML externo diretamente.
  6. Desenvolvedor: altere somente numa cópia de teste o intervalo de 10000 para 5000, meça o número de requisições e restaure o valor.
  7. Avançado: proponha um indicador de posição desatualizada quando timestamp tiver mais de 30 segundos, sem confundir horário local com UTC.
  8. Avançado: escreva um teste unitário para rejeitar longitude maior que 180 graus.

11. Próximas melhorias planejáveis

Primeiro, reconhecer automaticamente o tipo de ponte (simulador ou Bridge principal) e exibir a fonte de cada veículo. Segundo, mostrar idade da posição, estado online/offline e detalhes por dispositivo. Terceiro, implementar filtros, histórico e gráfico temporal de velocidade. Quarto, adicionar um mapa cartográfico real ao laboratório. Quinto, ligar o adaptador ao mapa 3D principal sem torná-lo dependente do Bridge. Finalmente, executar testes autenticados de ponta a ponta com o Traccar e dispositivos autorizados.

O que já foi testado: consulta dos quatro carros simulados, exibição na tabela e mudanças automáticas observadas pelo usuário; testes unitários anteriores do adaptador. O que ainda não foi comprovado: rastreamento físico real, autenticação Traccar → Bridge e renderização dos veículos no mapa 3D principal.
