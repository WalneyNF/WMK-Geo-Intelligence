1. O GPS não precisa de Python

GPS é um sistema de posicionamento. O dispositivo calcula ou recebe sua localização; um programa transporta essa posição; um servidor pode receber e armazenar; e a interface consulta e desenha os resultados. Python é apenas uma ferramenta possível para gerar ou transportar os dados.

Fonte de posição → protocolo de transporte → receptor/servidor
                                                   ↓
                                            armazenamento
                                                   ↓
                                         API REST / JSON
                                                   ↓
                                           mapa / tabela

Os campos básicos são: identificador do dispositivo, latitude, longitude e instante da posição. Velocidade, direção, altitude, bateria e precisão são opcionais conforme a fonte. Sem timestamp não é possível avaliar corretamente se a posição está atualizada.

2. Como os quatro carros funcionam no laboratório atual

simular-carros.py
  ├─ rotas fictícias em Nova Friburgo
  ├─ veiculos.json (cadastro)
  └─ posicoes-simuladas.jsonl (eventos)
                   ↓
wmk_bridge.py :8766
  └─ GET /api/v1/vehicles?source=simulator
                   ↓
geo-bridge-lab.js → bridgeAdapter.js
                   ↓
Tabela e pontos SVG no navegador

O simulador calcula posições intermediárias entre pontos de rotas, velocidade e direção. Ele registra eventos em um arquivo JSON Lines. A ponte lê o cadastro e os últimos eventos para construir a resposta JSON. O navegador consulta a API periodicamente, por padrão a cada dez segundos. O navegador não lê diretamente o arquivo Python ou JSONL.

O script simular-carros.py tem dois modos: por padrão demonstra e grava o JSONL sem enviar ao Traccar; com --enviar, tenta também enviar as posições por protocolo OsmAnd para http://127.0.0.1:5055/. O envio só é permitido para host local nessa implementação, e os identificadores devem estar cadastrados no Tracker.

4. Diferença entre protocolos e portas

EndereçoFinalidade
127.0.0.1:5055Receptor OsmAnd do Traccar, se habilitado.
127.0.0.1:8082Interface e API autenticada do Tracker.
127.0.0.1:8766Ponte Python do laboratório: simulador, consulta Traccar opcional e POST externo.
127.0.0.1:8768WMK Geo Bridge independente, com API própria e acesso ao Tracker configurável.
127.0.0.1:4173Servidor web de desenvolvimento do Geo Intelligence; não recebe GPS.

HTTP REST serve para consultar ou enviar dados por URLs. TCP/UDP transporta protocolos de rastreadores físicos. Polling é o navegador consultando repetidamente; não é transmissão contínua do dispositivo para o servidor.

5. Como trocar o Python por outro gerador de arquivos?

A ponte 8766 lê D:\Ferramentas\traccar\laboratorio-gps\veiculos.json e posicoes-simuladas.jsonl. Um programa de outra linguagem pode gerar o mesmo formato de eventos. Porém, isso é um acoplamento a arquivos de laboratório, não uma API pública estável. Não altere os arquivos em produção sem coordenação de escrita.

Exemplo de linha didática JSONL:

{"id":"WMK-NF-CARRO-001","lat":-22.2827,"lon":-42.5320,"velocidade_kmh":35,"direcao":90,"horario":"2026-11-07T00:55:13Z"}

Cada linha deve ser um objeto JSON completo. O id precisa corresponder a um registro em veiculos.json. A ponte usa a última linha válida de cada ID entre as últimas 5.000 linhas lidas. Por isso, registros muito antigos ou fora desse intervalo podem não aparecer.

6. Forma mais desacoplada: enviar posições por HTTP POST

A ponte 8766 possui o endpoint POST /api/v1/external/positions. Ele só aceita escrita quando o processo é iniciado com WMK_BRIDGE_WRITE_KEY. A chave deve ser enviada no cabeçalho X-WMK-API-Key. A posição enviada é registrada em external-positions.jsonl. O retorno esperado é HTTP 202, que significa aceito.

Atenção: essa entrada não alimenta automaticamente a tabela dos quatro veículos. O endpoint de leitura GET /api/v1/external/positions é separado e retorna eventos externos; ele não usa o mesmo contrato schemaVersion + items de veículos. Para aparecer no mapa ou na tabela, ainda é necessário implementar um adaptador de leitura ou unificar as fontes no servidor.

Configurar em PowerShell local

cd D:\Ferramentas\traccar\laboratorio-gps
$env:WMK_BRIDGE_PORT = '8767'
$env:WMK_BRIDGE_WRITE_KEY = Read-Host 'Crie uma chave de teste'
py -3 wmk_bridge.py

Use a porta 8767 para não interromper a ponte 8766 que já funciona. Não publique a chave no GitHub. O exemplo é somente para loopback e laboratório.

Enviar uma posição de teste

$chave = Read-Host 'Informe a chave da ponte'
$dados = @{
  id = 'EXEMPLO-001'
  latitude = -22.28
  longitude = -42.53
  simulated = $true
} | ConvertTo-Json
Invoke-RestMethod -Method Post `
  -Uri 'http://127.0.0.1:8767/api/v1/external/positions' `
  -Headers @{ 'X-WMK-API-Key' = $chave } `
  -ContentType 'application/json' -Body $dados

O servidor grava o timestamp no momento do recebimento. A implementação atual valida ID, latitude e longitude; outros campos como velocidade, direção e timestamp enviados pelo cliente não são preservados nesse registro. Para consultar o que foi aceito:

Invoke-RestMethod 'http://127.0.0.1:8767/api/v1/external/positions'

7. Exemplo Node.js: enviar sem Python

Execute no Node.js 18 ou superior, com a ponte 8767 configurada e a variável WMK_BRIDGE_WRITE_KEY disponível para o processo Node. Não coloque segredos no arquivo-fonte.

const chave = process.env.WMK_BRIDGE_WRITE_KEY;
if (!chave) throw new Error('Configure a chave no ambiente');
const resposta = await fetch(
  'http://127.0.0.1:8767/api/v1/external/positions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-WMK-API-Key': chave
    },
    body: JSON.stringify({
      id: 'NODE-001',
      latitude: -22.28,
      longitude: -42.53,
      simulated: true
    })
  }
);
console.log(resposta.status, await resposta.json());

O código demonstra o transporte HTTP. Para mostrar esse dispositivo no mapa, ainda será necessário adaptar a camada de leitura conforme explicado no módulo 11.

8. Exemplo PHP: integrar com sistemas empresariais

Este exemplo usa a extensão cURL. Execute no backend PHP, não exponha a chave em HTML ou JavaScript enviado ao navegador.

<?php
$chave = getenv('WMK_BRIDGE_WRITE_KEY');
if (!$chave) { throw new RuntimeException('Chave ausente'); }
$dados = json_encode([
    'id' => 'PHP-001',
    'latitude' => -22.28,
    'longitude' => -42.53,
    'simulated' => true
], JSON_THROW_ON_ERROR);
$curl = curl_init('http://127.0.0.1:8767/api/v1/external/positions');
curl_setopt_array($curl, [
    CURLOPT_POST => true,
    CURLOPT_POSTFIELDS => $dados,
    CURLOPT_HTTPHEADER => [
        'Content-Type: application/json',
        'X-WMK-API-Key: ' . $chave
    ],
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_TIMEOUT => 8
]);
$corpo = curl_exec($curl);
if ($corpo === false) { throw new RuntimeException(curl_error($curl)); }
$status = curl_getinfo($curl, CURLINFO_HTTP_CODE);
curl_close($curl);
echo $status . ' ' . $corpo;

O mesmo conceito pode ser aplicado em C#, Java e Visual FoxPro: montar JSON, enviar POST, incluir cabeçalho de autenticação e tratar códigos HTTP. Cada linguagem precisa de seu cliente HTTP.

9. E se o próprio navegador fornecer GPS?

navigator.geolocation.getCurrentPosition(
  pos => console.log({
    latitude: pos.coords.latitude,
    longitude: pos.coords.longitude,
    accuracyMeters: pos.coords.accuracy
  }),
  erro => console.error(erro.message),
  { enableHighAccuracy: true, timeout: 15000 }
);

Isso exige permissão do usuário e contexto seguro (HTTPS ou localhost). O navegador pode não fornecer localização precisa, especialmente em computadores sem receptor GPS. Não envie a chave de escrita da ponte diretamente do navegador; faça o envio por um backend autenticado. A Geolocation API é uma fonte possível, mas não está ligada automaticamente ao laboratório.

10. Como usar celular ou rastreador físico?

  1. Instale e configure o Tracker e entre com conta autorizada.
  2. Cadastre o identificador único do dispositivo.
  3. Escolha um aplicativo ou rastreador compatível com um dos protocolos suportados pelo Traccar.
  4. Configure o endereço e a porta do receptor de protocolo. Para OsmAnd, o exemplo de laboratório usa 5055.
  5. Autorize o dispositivo a enviar localização e verifique as permissões de rede e firewall.
  6. Confirme que o Tracker realmente recebeu a posição na interface ou API autenticada.
  7. Configure a ponte para ler o Tracker, e só então mostre os veículos no cliente web.
Não confunda: o endereço 127.0.0.1 no celular aponta para o próprio celular, não para seu computador. Para um dispositivo remoto acessar o servidor é necessário endereço alcançável, rede e configuração segura. Não exponha o Tracker ou a ponte diretamente à internet sem planejar TLS, autenticação e firewall.

O script Python atual também pode testar envio OsmAnd local com py -3 simular-carros.py --enviar, desde que a porta 5055 esteja ativa e os IDs cadastrados. Sem --enviar, os quatro carros continuam sendo apenas eventos locais de laboratório.

11. Como fazer outra fonte aparecer no mapa?

Existem dois caminhos arquiteturais:

Caminho A — usar o Tracker como núcleo

Fonte externa → protocolo suportado pelo Traccar → dispositivos/posições do Tracker → Bridge autenticado → cliente Geo Intelligence. É o caminho mais adequado quando você quer cadastro, histórico e suporte a rastreadores reais.

Caminho B — usar a ponte como gateway de dados

Fonte externa → POST autenticado na ponte → armazenamento de eventos → novo adaptador de normalização → /api/v1/vehicles ou endpoint de veículos compatível → interface. A parte em negrito ainda não foi implementada para os eventos externos.

O contrato esperado pelo cliente didático tem schemaVersion: "1.0" e items, cada item com id, name e position. Um evento externo isolado tem outro formato. Um adaptador deve fazer a correspondência entre IDs, guardar a última posição, validar coordenadas, tratar horários e marcar a fonte. Evite misturar dados reais com simulados sem sinalização explícita.

Registre data, fonte, ID, posição enviada, status HTTP e resultado observado. Para testes reais, use dispositivos próprios ou com consentimento.

13. Limitações técnicas e segurança

A ponte de laboratório lê um arquivo JSONL de até 5.000 linhas recentes para reconstruir a última posição de cada carro. Isso funciona para protótipos, mas não substitui um banco transacional com índices, retenção e controle de concorrência. O endpoint externo guarda somente os campos previstos; não unifica automaticamente fontes. A chave de escrita é simples e destinada a laboratório local; o GET de eventos externos não tem autorização por usuário. Não publique essa API na internet.

Em sistemas profissionais, recomendamos PostgreSQL/PostGIS ou outro banco adequado, autenticação e autorização por dispositivo, HTTPS, auditoria, tratamento de dados antigos, fila de ingestão, validação rigorosa, retenção de histórico e observabilidade. Dados de localização exigem cuidado especial com consentimento e LGPD.

14. Exercícios para desenvolvedores

  1. Crie um script Node que envia três posições fictícias com IDs diferentes.
  2. Crie um script PHP que consulta o GET de eventos externos e mostra uma tabela.
  3. Implemente, numa branch separada, um adaptador que converte eventos externos em items do contrato 1.0.
  4. Adicione velocidade, direção e timestamp ao contrato de entrada externa, com validação e testes.
  5. Crie um filtro de fonte: simulado, externo e Tracker, sem misturar identificadores.
  6. Mostre no mapa a idade da posição e sinalize quando estiver desatualizada.
  7. Implemente testes de erro para chaves inválidas, coordenadas fora de faixa e JSON malformado.
  8. Compare polling HTTP, WebSocket e MQTT em latência, segurança e complexidade.
